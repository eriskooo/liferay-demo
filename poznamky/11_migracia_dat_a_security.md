# 11 – Migrácia dát a security

## Čo sa naučíš

- Ako demo prenáša dáta z Liferay tabuľky `demo_task` do novej schémy cez Flyway
- Čo všetko treba pri migrácii dát vyriešiť (ID, null hodnoty, UTC, legacy stĺpce)
- Čo sa stane, keď Liferay a Spring Boot bežia súčasne nad tými istými dátami (overené: **kolízia ID**)
- Ako sa Liferay používatelia, role a oprávnenia nahrádzajú Keycloakom a Spring Security
- Ako vyzerá zapnutá security v deme bez bežiaceho Keycloaku

**Predpoklad:** kapitola 10 (Spring Boot beží nad DB z docker-compose a naimportoval Liferay úlohy).

---

## Časť A: Migrácia dát

### Teória v skratke

Demo používa najjednoduchšiu stratégiu: **jednorazový import SQL skriptom** v tej istej databáze.

```
 PostgreSQL "lportal" (docker-compose, port 5433)
 ┌───────────────────────────────────────┐     ┌──────────────────────────────────────┐
 │ schéma public  (vlastní Liferay)      │     │ schéma tasks  (vlastní Spring Boot)  │
 │                                       │     │                                      │
 │  demo_task                            │ V2  │  task                                │
 │   taskid, groupid, companyid, userid, │────>│   id, title, done, create_date,      │
 │   createdate, title, done             │     │   group_id, company_id, user_id      │
 │  user_, group_, layout, counter, ...  │     │  flyway_schema_history               │
 └───────────────────────────────────────┘     └──────────────────────────────────────┘
```

- **V1** vytvorí novú tabuľku `tasks.task` (snake_case, `NOT NULL`, dlhší `title`, ID z identity).
- **V2** skopíruje riadky z `public.demo_task`, ak tabuľka existuje, a posunie identity sekvenciu za najvyššie ID.
- Obe migrácie bežia **raz**. Flyway si to zapíše do `tasks.flyway_schema_history`.

V reálnom projekte sa namiesto jedného SQL skriptu často používa samostatný ETL proces (Spring Batch, vlastný migrátor, DB link), lebo DB sú na rôznych serveroch a dát sú milióny. Princípy sú však rovnaké.

### Kód z repa: [`V1__create_task.sql`](../spring-boot-tasks/src/main/resources/db/migration/V1__create_task.sql)

```sql
-- Pôvodná Liferay tabuľka (zo Service Builder tables.sql):
--   create table DEMO_Task (taskId LONG not null primary key, groupId LONG, companyId LONG,
--       userId LONG, createDate DATE null, title VARCHAR(75) null, done BOOLEAN);
create table task
(
    id          bigint generated by default as identity primary key,
    title       varchar(255) not null,
    done        boolean      not null default false,
    create_date timestamp    not null default (now() at time zone 'utc'), -- UTC ako Liferay
    group_id    bigint,
    company_id  bigint,
    user_id     bigint
);

create index ix_task_done on task (done);
```

| Liferay `demo_task` | Nová `task` | Prečo |
|---|---|---|
| `taskid` | `id` `generated by default as identity` | `by default` dovolí vložiť pôvodné ID pri importe, nové ID generuje DB |
| `title varchar(75) null` | `title varchar(255) not null` | 75 bolo len predvolené Service Buildera. Nová aplikácia vyžaduje title. |
| `done boolean` (nullable) | `done boolean not null default false` | žiadne tri stavy |
| `createdate timestamp` | `create_date timestamp not null` | v UTC |
| `groupid`, `companyid`, `userid` | `group_id`, `company_id`, `user_id` (nullable) | **legacy** referencie len pre dohľadateľnosť. Nová aplikácia ich nevyplňa a API ich nevystavuje. |

### Kód z repa: [`V2__import_liferay_tasks.sql`](../spring-boot-tasks/src/main/resources/db/migration/V2__import_liferay_tasks.sql)

```sql
DO
$$
    BEGIN
        IF to_regclass('${liferaySchema}.demo_task') IS NOT NULL THEN      -- bez Liferay tabuľky sa preskočí
            INSERT INTO task (id, title, done, create_date, group_id, company_id, user_id)
            SELECT taskid,
                   coalesce(nullif(trim(title), ''), '(untitled)'),         -- prázdny title → '(untitled)'
                   coalesce(done, false),
                   coalesce(createdate, now() at time zone 'utc'),          -- Liferay ukladá UTC
                   groupid, companyid, userid
            FROM ${liferaySchema}.demo_task
            ON CONFLICT (id) DO NOTHING;
        END IF;

        -- Zachovávame pôvodné ID (URL, referencie) → sekvenciu posunieme za maximum
        PERFORM setval(pg_get_serial_sequence('task', 'id'),
                       (SELECT coalesce(max(id), 0) + 1 FROM task), false);
    END
$$;
```

Čo všetko skript rieši:

1. **Názvy:** PostgreSQL ukladá Liferay tabuľky bez úvodzoviek, teda malými písmenami (`DEMO_Task` → `demo_task`, `taskId` → `taskid`).
2. **Placeholder `${liferaySchema}`:** Flyway ho nahradí hodnotou z `application.yml` (`spring.flyway.placeholders.liferaySchema: public`). Schéma sa dá zmeniť bez úpravy skriptu.
3. **Dátová kvalita:** Liferay dovoľoval `null` a prázdne hodnoty, nová schéma nie, takže skript ich nahradí predvolenými hodnotami.
4. **Zachovanie ID:** úlohy majú rovnaké ID ako v Liferay. Staré odkazy a referencie z iných systémov zostanú platné.
5. **Sekvencia:** nové ID musia začínať **za** najvyšším importovaným ID, inak by prvý `INSERT` spadol na duplicitný kľúč.
6. **Idempotencia:** `ON CONFLICT DO NOTHING` + `IF to_regclass(...)`. Skript nespadne na čistej DB (testy) ani pri opakovanom importe.

### Overené: čo sa stane pri súbežnom behu (kolízia ID!)

Po importe som nechal bežať **oba** systémy a v každom pridal úlohu:

1. Spring Boot: `POST /api/tasks` → nová úloha dostala **ID 103** (sekvencia za max 102).
2. Liferay: `POST /o/tasks` →

```
{"groupId":"20117","id":"103","title":"Pridané v Liferay po migrácii",...} HTTP 201
```

Liferay pridelil **tiež ID 103**. Jeho Counter mal rezervovaný blok 101–200 ([kapitola 06](06_service_builder.md)) a o novej sekvencii v schéme `tasks` nevie.

Výsledok:
- **dve rôzne úlohy s rovnakým ID** v dvoch systémoch,
- úloha z Liferay sa v Spring Boot **nikdy neobjaví**. V2 už prebehla a znova nebeží (`totalElements` zostal 6),
- zmeny sa rozchádzajú: úlohu 2 som v Spring Boot prepol na `done=true`, v Liferay `demo_task` zostala `done=false`.

**Ponaučenie na pohovor:** jednorazový import funguje, len ak sa v momente prepnutia **zastaví zápis v starom systéme** (cutover). Ak majú systémy bežať súbežne (strangler fig, [kapitola 12](12_migracna_strategia.md)), treba zvoliť jednu z možností:

| Stratégia | Ako | Nevýhoda |
|---|---|---|
| **Jeden zdroj pravdy** | Liferay portlet volá nové Spring API, alebo nový systém číta a zapisuje Liferay tabuľku | dočasná väzba na starú schému |
| **Oddelené rozsahy ID** | sekvencia v novom systéme začína napr. na 10 000 000, alebo UUID | ID už nie sú „pekné“, treba to dohodnúť |
| **Synchronizácia (CDC)** | zmeny z Liferay tabuľky sa priebežne prenášajú (napr. Debezium) | infraštruktúra navyše, riešenie konfliktov |
| **Big-bang cutover** | read-only režim v Liferay, finálny import, prepnutie | výpadok, nutná skúška nasucho (dry run) |

### Ďalšie pasce pri migrácii Liferay dát

| Pasca | Prečo | Riešenie |
|---|---|---|
| **UTC** | Liferay JVM beží v GMT a časy v DB sú v UTC bez zóny (`timestamp without time zone`) | `Instant` v entite + `hibernate.jdbc.time_zone: UTC` (v deme) |
| **ID ako reťazec** | Liferay JSON vracia `"id":"103"`, Jackson `103` | dohodnúť kontrakt s klientmi, prípadne `@JsonFormat(shape = STRING)` |
| **Counter** | ID nie sú zo sekvencie, majú diery, rezervujú sa bloky | sekvencia za max ID, nespoliehať sa na súvislé ID |
| **`groupId` / `companyId`** | multi-tenancy Liferay (site, inštancia) | mapovať na tenant ID, alebo zahodiť, ak je len jeden site |
| **`userId`** | odkazuje na `user_` v Liferay | mapovať na používateľa v Keycloaku (napr. cez e-mail alebo external ID), alebo uložiť ako legacy |
| **Lokalizované polia** | Liferay ukladá preklady ako XML v jednom stĺpci (napr. `group_.name` site Guest: `<root available-locales=...><Name language-id="en_US">Guest</Name></root>`) | parsovať XML, rozdeliť do tabuľky prekladov |
| **Súbory (Documents & Media)** | v DB sú len metadáta, súbory sú v `data/document_library` (alebo S3) | migrovať súbory zvlášť a mapovať cesty |
| **Cache** | Liferay drží entity v cache, priamy SQL zápis do jeho tabuliek neuvidí | do Liferay tabuliek zapisovať cez jeho API, alebo potom vyčistiť cache |

## Časť B: Security

### Teória v skratke: čo dáva Liferay

V Liferay je security súčasťou portálu:

| Liferay | Čo to je |
|---|---|
| **Users** (`user_`) | používatelia s heslom v Liferay DB, prípadne LDAP/SSO |
| **Roles** | Regular (celý portál), Site, Organization. Napr. Administrator, Power User, User, Guest. |
| **Permissions** | per akcia a per objekt (`resourcepermission`): kto smie VIEW, UPDATE, DELETE, ADD_ENTRY… |
| **Kontrola v kóde** | `PermissionChecker`, `ModelResourcePermission.check(...)`, remote servisy |
| **Portlet roly** | `javax.portlet.security-role-ref=power-user,user` |
| **Session + CSRF** | prihlásenie cez formulár, session cookie, token `p_auth` |
| **REST autentifikácia** | auth verifiers: Basic, session, OAuth2 (Liferay ako authorization server) |

V Spring Boot nič z toho nie je. Typická náhrada:

```
                  ┌────────────────────┐
  používateľ ───> │ Keycloak (IdP)     │  používatelia, heslá, role (realm "liferay-migration")
  (Angular)       │  OAuth2 / OIDC     │  migrácia z Liferay: LDAP federácia alebo import
                  └─────────┬──────────┘
                            │ JWT access token (realm_access.roles = ["tasks-editor"])
                            v
                  ┌────────────────────┐
                  │ Spring Boot API    │  OAuth2 Resource Server
                  │  overí podpis JWT  │  role z tokenu → ROLE_tasks-editor
                  │  @PreAuthorize /   │  pravidlá podľa URL a HTTP metódy
                  │  requestMatchers   │
                  └────────────────────┘
```

- **Keycloak** prevezme správu používateľov a rolí (namiesto `user_`, `role_`). Prihlásenie robí Keycloak, nie aplikácia.
- **Spring Boot** je **resource server**: hesla nevidí, len overí podpis JWT tokenu a z neho vyčíta role.
- **Jemné oprávnenia per objekt** (Liferay `resourcepermission`) zmiznú. Treba ich nahradiť explicitnou logikou (vlastník záznamu, `@PreAuthorize("@taskSecurity.canEdit(#id)")`, ACL tabuľka). Je to často najťažšia časť migrácie.

### Kód z repa: [`SecurityConfig.java`](../spring-boot-tasks/src/main/java/com/example/tasks/config/SecurityConfig.java)

Dva režimy podľa `tasks.security.enabled`:

```java
public static final String ROLE_VIEWER = "tasks-viewer";
public static final String ROLE_EDITOR = "tasks-editor";

/** Produkčný reťazec: JWT z Keycloaku + role per HTTP metóda */
@Bean
@ConditionalOnProperty(name = "tasks.security.enabled", havingValue = "true")
public SecurityFilterChain oauth2FilterChain(HttpSecurity http) throws Exception {
	JwtAuthenticationConverter jwtConverter = new JwtAuthenticationConverter();
	jwtConverter.setJwtGrantedAuthoritiesConverter(new KeycloakRealmRoleConverter());

	return http
			.csrf(csrf -> csrf.disable())   // bezstavové API bez cookies → CSRF nehrozí (≈ náhrada p_auth)
			.sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
			.authorizeHttpRequests(auth -> auth
					.requestMatchers(PUBLIC_PATHS).permitAll()                                   // swagger, health
					.requestMatchers(HttpMethod.GET, "/api/tasks/**").hasAnyRole(ROLE_VIEWER, ROLE_EDITOR)
					.requestMatchers("/api/tasks/**").hasRole(ROLE_EDITOR)                      // zápis len editor
					.anyRequest().authenticated())
			.oauth2ResourceServer(oauth2 -> oauth2.jwt(jwt -> jwt.jwtAuthenticationConverter(jwtConverter)))
			.build();
}

/** Lokálne demo bez IdP: všetko povolené (NIKDY v produkcii) */
@Bean
@ConditionalOnProperty(name = "tasks.security.enabled", havingValue = "false", matchIfMissing = true)
public SecurityFilterChain openFilterChain(HttpSecurity http) throws Exception { ... permitAll() ... }
```

[`KeycloakRealmRoleConverter.java`](../spring-boot-tasks/src/main/java/com/example/tasks/config/KeycloakRealmRoleConverter.java): Keycloak dáva role do claimu `realm_access.roles`. Spring Security ich štandardne nečíta, preto converter:

```java
public Collection<GrantedAuthority> convert(Jwt jwt) {
	Map<String, Object> realmAccess = jwt.getClaimAsMap("realm_access");
	if (realmAccess == null || !(realmAccess.get("roles") instanceof Collection<?> roles)) {
		return List.of();
	}
	return roles.stream()
			.map(String::valueOf)
			.map(role -> (GrantedAuthority) new SimpleGrantedAuthority("ROLE_" + role))   // tasks-editor → ROLE_tasks-editor
			.toList();
}
```

Profil [`application-keycloak.yml`](../spring-boot-tasks/src/main/resources/application-keycloak.yml):

```yaml
tasks:
  security:
    enabled: true
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          # Realm, kam sa migrujú Liferay používatelia a role (napr. cez LDAP federáciu alebo export)
          issuer-uri: http://localhost:8180/realms/liferay-migration
```

Mapovanie rolí (návrh pre demo):

| Liferay | Keycloak realm rola | Spring |
|---|---|---|
| Guest | – (bez tokenu) | `401` |
| User / Power User (len čítanie úloh) | `tasks-viewer` | `GET` povolené, zápis `403` |
| Power User / Administrator (správa úloh) | `tasks-editor` | všetko |
| Permission `VIEW`/`UPDATE` na konkrétnu úlohu | – | treba doplniť logiku per objekt |

V logu je vidno, že Spring sa pokúsil stiahnuť konfiguráciu z Keycloaku:

```
JwtDecoderInitializationException: Failed to lazily resolve the supplied JwtDecoder instance
Caused by: IllegalArgumentException: Unable to resolve the Configuration with the provided Issuer of "http://localhost:8180/realms/liferay-migration"
Caused by: ResourceAccessException: I/O error on GET request for "http://localhost:8180/realms/liferay-migration/.well-known/openid-configuration": Connection refused
```

Takto funguje `issuer-uri`: Spring si z `/.well-known/openid-configuration` zistí, kde sú verejné kľúče (JWKS), a nimi overuje podpis tokenov. S bežiacim Keycloakom by si token získal napríklad cez `POST /realms/liferay-migration/protocol/openid-connect/token`.

Aplikáciu ukonči `Ctrl+C`.

## Časté chyby

| Príznak | Príčina | Riešenie |
|---|---|---|
| `duplicate key value violates unique constraint "task_pkey"` pri prvom POST po importe | Sekvencia nebola posunutá za importované ID | `setval(...)` ako v V2 |
| Nové dáta z Liferay sa v Spring Boot neobjavia | V2 je jednorazová migrácia | Cutover (zastaviť zápis v Liferay) alebo synchronizácia |
| Rovnaké ID v Liferay aj Spring Boot | Liferay Counter a nová sekvencia o sebe nevedia | Oddelené rozsahy ID, UUID, jeden zdroj pravdy |
| Časy posunuté o 1–2 h | Liferay ukladá UTC, Spring číta v lokálnej zóne | `Instant` + `hibernate.jdbc.time_zone: UTC` |
| `Validate failed: Migration checksum mismatch` | Zmenil si už aplikovaný Flyway skript | Aplikované skripty nemeniť, pridať nový `V3__...` |
| `401` aj so správnym tokenom | Iný `issuer` v tokene ako `issuer-uri`, alebo Keycloak nedostupný | Porovnaj claim `iss` s `issuer-uri`, over dostupnosť `/.well-known/openid-configuration` |
| `403` so správnym používateľom | Role nie sú v `realm_access.roles` alebo chýba prefix `ROLE_` | `KeycloakRealmRoleConverter`, skontroluj obsah tokenu (jwt.io) |

## Otázky na pohovor

**Ako by si migroval dáta z Liferay Service Builder tabuliek?**
Zmapujem schému (`service.xml`/`tables.sql` → nová schéma), napíšem idempotentný migračný skript alebo ETL: zachovanie ID, ošetrenie `null` a prázdnych hodnôt, UTC, legacy stĺpce, nastavenie sekvencie. Otestujem ho na kópii produkčných dát (Testcontainers so simulovanou schémou). Pred ostrým prepnutím spravím skúšku nasucho a porovnám počty a kontrolné súčty.

**Čo s ID z Liferay?**
Ak na ne odkazujú URL alebo iné systémy, zachovať ich a sekvenciu nastaviť za maximum. Liferay ID pochádzajú z Counteru, nie zo sekvencie, a majú diery. Pri súbežnom behu hrozí kolízia, ktorú treba riešiť oddelenými rozsahmi, UUID alebo jedným zdrojom pravdy.

**Ako zabezpečiť konzistenciu dát, keď staré a nové riešenie bežia súčasne?**
Jeden systém musí byť zdrojom pravdy pre danú entitu. Buď starý systém volá nové API, alebo sa dáta synchronizujú (CDC, napr. Debezium) s jasným smerom. Alternatívou je krátky cutover s read-only režimom v Liferay.

**Ako nahradíš Liferay používateľov a role?**
Identity provider (Keycloak): import používateľov alebo LDAP federácia, ak Liferay už čerpal z LDAP. Heslá sa z Liferay preniesť nedajú (hash), takže treba reset alebo federáciu. Role mapujem na realm/client role, aplikácia je OAuth2 resource server a role číta z JWT. Jemné permissions per objekt treba prepísať do aplikačnej logiky.

**Prečo je v Spring Boot vypnuté CSRF a v Liferay nie?**
Liferay používa session cookie, prehliadač ju posiela automaticky, preto treba CSRF token (`p_auth`). Spring API je bezstavové s Bearer tokenom v hlavičke, ktorý prehliadač sám nepošle, takže CSRF útok nemá čo zneužiť. Ak by API používalo cookies, CSRF ochrana musí zostať.

**Čo je OAuth2 resource server?**
Aplikácia, ktorá prijíma access tokeny (JWT) a overuje ich podpis voči verejným kľúčom IdP (JWKS z `issuer-uri`). Sama prihlásenie nerieši. Z tokenu číta identitu a role a podľa nich povoľuje prístup.
